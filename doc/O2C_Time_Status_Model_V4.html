Status & flag model V4 — build it to be replaced

Two status axes, at two grains, with a disclaimer saying it will change again. That last part should decide the architecture, not be a footnote to it.

13 August 2026 · read from the four visible sheets — Statuses, Flags, Scenarios, Other requirements · supersedes the revision-2 model in CLAUDE.md §7 · phase 1 is built (db/27_status_model_v4.sql); the backdated-change rule in §7 is confirmed

The disclaimer is the most important line in the mail

"This might undergo changes as we build integrations. Kindly structure the code accordingly."

Taken seriously, that rules out the obvious implementation. Statuses in CHECK constraints, flags as boolean columns and transitions as IF/ELSE in PL/SQL all mean the next revision is a schema migration plus a package rewrite plus a regression pass. Every one of those should be data instead.

The rest of this plan is mostly that decision applied consistently.

Scenario 14 is Defaulted / Manager Defaulted — both cut-offs missed. Scenario 16 is Defaulted / Approved. Neither can be held in one column, and today the module loses half of each.

DEFAULTED_BY exists only because one column could not say whose cut-off was missed. Split the axes and it becomes redundant — which is a good sign: this is the shape the module has been approximating, not a different one.

2 · And two grains — status lives on the day as well

This is the part that changes the table design rather than just the columns.

OC_TS_ENTRY already has DAY_STATUS with Pending / Approved / Rejected — a day-level approval axis, half-built and unnamed as such. V4 wants both axes and flags at both grains.

Decide this early: is the week derived, or maintained alongside?

Two readings, and they lead to different code.

Derived (recommended). The day is the truth; the week is a materialised rollup — all days approved → week Approved, any day rejected → week Rejected. This matches how the workbook behaves: a backdated change to one day invalidates the whole week. It also matches SC-08, day-wise approval, which already exists.

Independent. Both set separately. More flexible, and it permits a week saying Approved while a day says Rejected — a contradiction somebody will eventually have to explain to finance.

I would derive. But the rollup rule for each combination has to be written down before it is coded, because "any day rejected → week Rejected" is a choice, not a fact.

Collapsing three into one loses nothing, because the detail was never in the flag

The flag was only ever a summary — the specifics live in the rows and stay exactly where they are:

  • Advance closure → OC_TS_MONTH_CONFIRM.CONFIRM_TYPE, which records that a month went to accrual unapproved, and when, and by whom
  • Reversal → OC_TS_ENTRY.ENTRY_TYPE, plus the signed HOURS that make a reversal a reversal

So "why was this adjusted" is still answerable in one join. The screen shows one chip instead of three, which is also an improvement.

"Every flag should be maintained with time stamp" is what makes flags rows rather than columns. Six booleans today record that something happened and never when.

OC_TS_WEEK_FLAG                      OC_TS_DAY_FLAG
  ts_week_id                           ts_entry_id
  flag_code   → OC_TS_FLAG_DEF         flag_code   → OC_TS_FLAG_DEF
  set_on      TIMESTAMP                set_on      TIMESTAMP
  set_by      VARCHAR2(100)            set_by      VARCHAR2(100)
  cleared_on  TIMESTAMP                cleared_on  TIMESTAMP
  PK (ts_week_id, flag_code)           PK (ts_entry_id, flag_code)

Two tables rather than one polymorphic table, so both keep a real foreign key. The old boolean columns become a view, and nothing reading them breaks on day one.

4 · The transition table — where the disclaimer pays off

Section 2 of the Scenarios sheet is sixteen rows of one rule. Those rows should be data.

OC_TS_TRANSITION
  event_code        DailyChange | Submit | Approve | Reject |
                    WeeklyCutoff | DeliveryCutoff | …
  from_submission   null = any
  from_approval     null = any
  period_state      Open | Closed | null = any
  require_flag      null = any    <- how "was ever Defaulted" survives
  to_submission     the new value
  to_approval       the new value
  raise_flag        null, or the flag to set
  match_order       lowest wins, so specific beats catch-all

The whole of section 2 loads as rows. When V5 arrives with different combinations, you reload the table and the package does not change.

The alternative — sixteen branches of PL/SQL — has to be re-read, re-tested and re-reviewed every revision, and the workbook has told you in advance that there will be revisions.

This is also what closes O3

The sync change-capture layer is live and queues every master-data change as Pending in OC_TIME_SYNC_CHANGE, with nothing draining it — that has been O3 since the capture was built.

Section 2 is the drain rule. Load it into OC_TS_TRANSITION, point the daily process at it, and O3 closes as a side effect rather than as a separate project.

7 · The backdated-change rule — confirmed

Confirmed 13 August · this decides every row in section 2

A backdated change sets Approval → Rejected and Submission → Not Yet Submitted. Both axes move — the prior approval is void and the week goes back to the employee.

The Scenarios sheet writes this as Rejected | Not Yet submitted under headers reading Employee Status | Manager Status, which looks like the two columns swapped. It is not an error in the sheet: that cell is shorthand for "sent back", and both values are the new state rather than one per column.

Everywhere else the labelled Employee | Manager order holds exactly. Scenarios 4, 5, 8, 9, 12, 14 and 16 all parse cleanly against it — Defaulted | Manager Defaulted, Late submission | Approved, Submitted | Manager Defaulted — so section 2's phrasing is the single exception, not a systematic reversal.

The alternative reading would have left a manager's approval standing on hours that had since changed. That is a defect rather than a design, which is why the logic pointed here before the confirmation did.

  • Daily process drains OC_TIME_SYNC_CHANGE through the same engine
  • R1 contractor window · R5 action date

Phase 3 · Screens

  • Manager filters gain the approval axis · R6 adjustment reasons
