O2C Timesheet Module · Integration

Building the OIC master-data sync

Two integrations, six feeds, two schedules. Everything below marked verified was called against the live SIT endpoints and the dev20 pod; everything marked unproven has not been run yet.

11-Aug-2026 ords-sit.rite.digital/ords/o2c_time supersedes O2C_Time_OIC_Build_Guide §1.1, §3

whyWhat changed since the last guide

The earlier build guide was written on 09-Aug, before the sync endpoints existed. Two of its sections are now actively misleading:

§1.1 “The watermark cannot filter anything”

True when written — no extract had a LAST_UPDATE_DATE predicate, so it recommended a full refresh on every run. :P_LAST_SYNC was added exactly as that section’s own closing note proposed. Measured on the pod: passing 2026-08-01 returns 12 workers and 9 allocations instead of 5850 and 543. The delta is real; do not build a full refresh.

§3.3–3.4 stageAndTransform / chunked postToOrds

Describes posting rows to the per-entity JSON endpoints. Those still exist but key differently and are not this path. There is now a single endpoint that takes the BIP XML verbatim, so the staging scope and the chunked post both disappear.

1The shape

OIC carries no field mapping and no SQL. It knows how to read a config row, run a report, and hand the bytes over. Everything about which columns exist and how a row is matched lives in the database, next to the tables it writes.

001
Orchestrator — one per schedule

Reads the config, loops the feeds in run order, calls the child for each, then triggers population.

002
Child — built once, called six times

Runs one BIP report with two parameters, decodes the response, posts the XML to ORDS, reads the result.

2What ORDS hands you verified

GET /oc/time/sync/config?scheduleTag=Monthly — returned 200 with six rows. This is the whole input to the orchestrator.

The keys are lowercase

ORDS returns lastsyncdate, not lastSyncDate — the camelCase aliases in the handler’s SELECT are not preserved. A mapper written against the camelCase name resolves to nothing and reports no error.

Run order is data, not decoration — OC_TIME_ALLOCATION has foreign keys to both worker and project, so an allocation whose worker has not loaded lands in OC_TIME_SYNC_FAILED instead of the table:

3The child integration

3.1
Run the report

ExternalReportWSSService → runDataModel, at reportpath, with both parameters:

P_LAST_SYNC
← lastsyncdate
P_EFFECTIVE_DATE
← effectivedate

Both YYYY-MM-DD, both straight through — no expression, no date maths. All eleven reports take the same two, so there is no per-report branching.

3.2
Decode

The XML comes back base64-encoded in <reportBytes>. Decode before posting. Responses may also be gzipped depending on the front end — including SOAP faults, so a failure can arrive as binary.

3.3
Post it

POST /oc/time/sync/load/{reportname} with Content-Type: application/xml and the decoded XML as the raw body — not a field inside a JSON envelope. The target table is looked up from the config by report name; you do not send it.

3.4
Read the result 
{"reportName":"CALENDAR","targetTable":"OC_TIME_CALENDAR",
 "status":"Success","rowsRead":1,"rowsMerged":1,
 "message":"1 of 1 row(s) merged into OC_TIME_CALENDAR."}
CodeMeansDo
200mergedlog rowsRead/rowsMerged, continue
404report not configured or disabledstop — a config fault, retrying will not help
422load refused; message names the rulestop the feed, keep going with the rest
500unexpectedretry once, then fault

422 and 500 are deliberately distinct: one will never succeed on retry, the other might.

The monthly effective date is next month, not today

The monthly run builds next month, so the HCM as-of date must fall inside it — otherwise you populate September from August’s allocations, and it looks entirely normal doing so. ORDS computes this and returns it, so the mapper never does date arithmetic; December→January is where hand-rolled month maths breaks.

An empty body on populate means everybody

The same endpoint scoped to one person is what the timesheet page calls on every load. Passing employeeId is the difference between one worker and the whole company — be deliberate about leaving it out.

A null targetperiodid means next month has no OC_TIME_PERIOD row yet. Nothing creates periods automatically, so the monthly run would have nothing to build — check it before the 28th.

7Open before go-live

  • Deletions are undetectable. An incremental delta returns changed rows; a removed one returns nothing. Accepted on the basis that allocations are end-dated rather than deleted — an end-dated row does come back. Worth confirming that is always the practice.
  • Future prepopulated days. A retro reallocation adjusts up to today; days already populated beyond it still carry the old project and want re-populating, not adjusting.
  • Employee cut-off for adjustments currently reads DELIVERY_CUTOFF. If it should be the payroll cut-off, that is one line.
  • Period control invoked from the O2C main application is still pending.
  • Adjustment generation rules await the flag/scenario workbook. Capture is live and queues everything Pending meanwhile, so nothing is lost while it is out.
