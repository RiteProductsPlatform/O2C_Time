O2C · Time Module · for review

Scope and integration

What the module does, what it deliberately does not do, every piece of data fetched live from Oracle Fusion as a screen loads, how time is prepopulated, the complete status and flag model, exactly what is posted back to Oracle Project Costing, and the end-to-end flow with every status transition.

Version 2.0 Prepared 05-Aug-2026 Source: REQ-PACK-TIME-001 v0.3 Branch O2C_Time_Integration

1Scope

Oracle Time & Labor is being replaced for project time capture and approval. Oracle remains the system of record for costing: we capture and approve time, then post approved hours to Project Costing.

In scope

  • All reference data read live from Fusion at page load — project, POET, task, allocation, rate, work schedule, shift pattern, calendar and absence (§2).
  • Time capture — day-wise entry per project and WBS task, multiple lines per day, quarter-hour granularity.
  • Prepopulation from allocation percentage and from approved absences (§3.1).
  • Approval — day, week and project-month, with reason and remarks on rejection, and an undo for a decision taken by mistake.
  • Manager override of hours with the employee’s original value retained.
  • Retro adjustments on a closed month, as a matched reversal and re-entry.
  • Cut-off enforcement — weekly (employee) and delivery (manager), with automatic defaulting at each.
  • Leave-loss / cover identification for absence on billable allocation.
  • Month confirmation to the O2C accrual interface.
  • Post to Oracle Project Costing via unprocessedProjectCosts (§4).
  • Own sign-in and roles — employee, contractor, manager, finance administrator.

Out of scope

  • Payroll — entirely out of scope. No hours are transferred to Global Payroll, nothing is written to elementEntries, no Payroll Time Type is resolved and no payroll reference data is read.
  • Salary hold — removed from scope for now. The module does not signal, hold or release anyone’s pay. A week that missed the weekly cut-off is still marked Defaulted and locked, and DEFAULTED_BY still records whether the employee or the manager missed it — but nothing downstream follows from that.
  • Daily and monthly scheduled sync — out of scope. There is no batch extract and no staged copy of Fusion data. Everything is fetched when a screen needs it. The existing extract feature is being removed (§2.3).
  • Invoice generation and revenue calculation.
  • Writing to Project Costing beyond the unprocessed-cost post — costing, burdening and accounting stay Oracle’s.
  • Absence creation. Absences are read from Absence Management and shown read-only; never created or amended here.
  • Calendar and shift authoring. Read from Fusion; no maintenance screen.
  • Period control screen. Periods and cut-offs are reference data, exposed read-only.
  • Mobile — phase 2.
  • Direct Fusion calls from the browser with credentials in the client (NFR-005). All Fusion traffic is server-side or proxied.
  • Timesheet upload (CSV in). Download exists; upload is on hold by decision.
Under discussion — independence from OTL. Whether this module should be fully independent of Oracle Time & Labor, or continue to interoperate with it, is not yet decided. The build reflects that: the push of approved time into OTL exists in the design but is on hold and nothing is sent (§3.5). The Project Costing post in §4 does not depend on OTL either way, so the decision can be taken without reworking it.

2Inbound integration — everything live from Fusion

One mechanism, not two. All reference data is fetched from Fusion at the point the screen needs it, by REST where a REST resource exists and by a direct BIP report call over SOAP where it does not. Nothing is extracted to a local copy first and nothing is read from a staged table.

2.1 What is fetched, and why

INT-006 Absence

Why: leave appears as read-only hours so the week reconciles to standard hours, and absence on a billable allocation is what triggers leave-loss. The query must be keyed on the person and the date. A scheduled extract cannot answer “is this person on leave on this date” for a date it did not cover, and leave is booked continuously — so a copied answer is wrong for exactly the days a timesheet is about.

2.2 REST or BIP — how each call is made

The choice is not a preference. Where Fusion exposes a REST resource that answers the question, we call it. Where it does not, we call the BIP report directly — SOAP runReport against ExternalReportWSSService, response decoded and used immediately. A BIP report called live is still a live read; what is being removed is the extract-to-a-table-and-read-it-later pattern, not BIP itself.

Oracle’s own REST documentation states that a person’s assigned work schedule is not a first-class REST resource, so the work-schedule and shift-pattern reads are the ones most likely to need BIP. The delivered views HTS_WORKERS_WITH_SHIFTS_V and HTS_SCHEDULES_DAY_SHIFT_VIEW already return the worker × day × shift shape the grid needs.

2.3 What is being removed

The current build extracts Fusion master data on a schedule into local cache tables and reads those. That feature is being removed. No daily sync, no monthly master sync, no staged copy.

Three consequences to confirm before build. (a) Prepopulation moves from a monthly batch to page load. Today a scheduled job builds every employee’s month in advance by walking the cached allocations. With no cache there is nothing to walk, so the week must be built when the employee first opens it. That is consistent with fetching as needed, and it means opening a month for the first time is slower than opening it again. (b) Fusion availability becomes a hard dependency. With a cache, a pod outage was invisible to the employee. Without one, a timesheet cannot be opened while Fusion is unreachable. Whether that is acceptable is a business call. (c) Sign-in still needs to know who people are. Identity, the manager hierarchy and the finance-administrator login are not in the list above, and sign-in cannot wait on a Fusion round trip — the administrator is a real login who need not exist as a worker in HCM at all. A decision is needed on whether worker identity remains local.

3The time module — prepopulation, status and flags

3.1 What is prepopulated, how, and when

Two passes, in this order, when the month is opened.

Pass 1 — allocated project time

StepRule
Skip the dayif it is a non-working day for that person’s location — weekend or holiday. Nothing is seeded, not even a zero. Saturday and Sunday still appear as blank, enterable cells.
Hoursstandard hours for that day × allocation % ÷ 100, rounded to the nearest quarter hour. A null allocation percentage is treated as 100. An 8-hour day at 50% seeds 4.00.
Taskthe project’s first chargeable WBS task in sort order — see the question below. If the project has none, nothing is seeded for that allocation and the reason is recorded as an exception, visible rather than silent.
Markingthe row is stamped SOURCE = 'Prepopulated' and ENTRY_TYPE = 'Actual'.
Idempotentan existing row for the same week × project × task × day is never overwritten, so re-opening a month never destroys typed hours.
Question for functional — how should hours spread across tasks? A project has four chargeable tasks and the person is allocated 100%.

What the build does today: it seeds one line only — the first chargeable WBS task in sort order — carrying the whole apportioned figure. On an 8-hour day that is 8.00 against one task, not 2.00 against each of four. Allocation percentage apportions between projects, never between tasks within a project, because Fusion holds the allocation per project and it carries no task-level split.

What we need confirmed: is one seeded line correct, with the employee moving hours onto the right tasks themselves — or should the figure be divided across the chargeable tasks? If it should divide, we need the rule for how: evenly, or by a weighting Fusion does not currently supply. Note that personAssignmentLaborSchedules can carry a per-POET percentage split, which is the only place a task-level weighting could legitimately come from.

Our recommendation: keep one line. An evenly divided figure looks authoritative and is almost always wrong, and a wrong number that has been pre-filled is less likely to be corrected than a blank one.

Pass 2 — approved absences

Approved absences are written as read-only leave rows at their own duration, against a common LEAVE task, marked IS_LEAVE = 'Y'. Allocation percentage is not applied — leave is whole. The absence is read live for that person and those dates (§2.1).

The leave row is written into the timesheet rather than merely displayed, because leave hours feed the week total, the leave-loss calculation and the accrual figures — a display-only overlay would leave all three short.

Open. An entry requires a project, so a leave row must attach to one of the person’s allocations. An employee with no active allocation has nowhere to hang their leave and the row is dropped silently. Needs a rule: the organization project, the last allocation held, or reported as an exception.

Pass 1 also runs at these points

TriggerWhat it covers
Employee opens a monthBuilds that person’s weeks for that month from data fetched at that moment. The primary path.
Weekly cut-offAn unsubmitted week is auto-submitted with default hours, marked Defaulted, and locked against further employee edits.
Delivery cut-offA week the manager never decided is marked Defaulted. It is not locked.

The two cut-off runs are the only remaining scheduled work, and they process time already captured rather than fetching reference data. They are independent of each other and of any other job.

3.2 Status

A record is in exactly one status at a time, at each grain.

GrainTable · columnValues
Week (the main one) OC_TS_WEEK.WEEK_STATUS Not yet submitted · Submitted · Approved · Rejected · Defaulted · Overridden and approved (6)
Day OC_TS_ENTRY.DAY_STATUS Pending · Approved · Rejected (3)
Project-month OC_TS_MONTH_CONFIRM.CONFIRM_TYPE Normal · Advance closure · Reopened (3)
Retro adjustment OC_TS_ADJUSTMENT.STATUS Awaiting Approval · Approved · Rejected · Cancelled (4)
“Closed” is removed. The week model ends at Approved. Confirming a month previously moved every approved week to a seventh status, Closed; it no longer does. The month-level confirmation is a fact about the month and is recorded in OC_TS_MONTH_CONFIRM, which is where anything needing to know “has this month gone out” should look. This is a build change, not only a documentation one: the status is still permitted by a database constraint and is still written by the confirm step, and both need amending.

3.3 Flags

A flag is not a status. Status is where the record has got to; a flag records something that happened on the way and stays true afterwards. A week carries any number of flags at once, all held on OC_TS_WEEK.

FlagColumnSet byMeaning
Defaulted DEFAULTED_FLAG
DEFAULTED_BY
LOCKED_FLAG		 the two cut-off runs Hours were filled in by a cut-off run rather than by a person. DEFAULTED_BY distinguishes EMPLOYEE — missed the weekly cut-off, which locks the week against further employee edits — from MANAGER, missed the delivery cut-off, which does not lock. The lock is a property of this flag, not a flag of its own. The distinction is kept because it records whose deadline passed, which the audit needs regardless.
Late submission LATE_SUBMISSION_FLAG submit, when past the cut-off The week arrived after the cut-off. A flag, not a status — the week is still Submitted. Never cleared: revoking or resubmitting does not un-happen it.
Advance closure ADVANCE_CLOSURE_FLAG advance approval of a future month The month was closed ahead of its cut-off; defaulted hours in it are treated as approved.
Overridden & approved OVERRIDDEN_FLAG manager override A manager changed the hours and approved them. The employee’s original value is retained in the audit trail. Also a week status — see 3.4.
Reversal HAS_REVERSAL_FLAG derived automatically The week contains at least one negative reversal row. Recomputed from the entries, never set by hand.
Adjustment HAS_ADJUSTMENT_FLAG derived automatically The week contains at least one retro adjustment row. Same derivation.

Six flags. There is no separate “Locked” flag — locking is what Defaulted by employee does.

3.4 How status and flag relate

  1. Orthogonal. One status, many flags. A week can be Submitted + Late submission + Adjustment simultaneously.
  2. Two values are both. Defaulted and Overridden and approved appear as a week status and as a flag. The status says what the week is now; the flag says it happened at all and survives a later transition — a defaulted week that a manager then approves becomes Approved while the defaulted flag stays set. Whether to keep this duplication is an open item.
  3. Precedence, when only one label can be shown. The accrual interface and the chips on screen must pick one. Most specific first: row is a Reversal → row is an Adjustment → Advance closure → Overridden & approved → Defaulted → Late submission → none.

Where each is maintained

Rejection carries a reason — Manager, Client or Absence — and it is mandatory, enforced by a database constraint rather than by the screen. Remarks are free text.

3.5 Outbound destination status

Held on OC_TS_MONTH_CONFIRM, one column per destination, each taking Pending · Success · Failed · Skipped. They are separate on purpose: the destinations fail independently, and a single combined column loses which one needs attention.

ColumnDestinationState
ACCRUAL_STATUS The O2C accrual interface table. The consumer reads from it. Live. Filled on month confirm.
PARTNER_STATUS A staging table in our own schema that the accrual module pulls from. It holds three things for a confirmed month: the summary, the complete timesheet employee-wise, and any adjustments. We write it; accrual reads it. Nothing is pushed into accrual’s tables. Structure pending. The accrual side is defining the shape and that work is in progress, so the columns are not fixed yet. The direct push that previously occupied this column is superseded — see the note below.
OTL_STATUS Oracle Time & Labor — the push of approved time into OTL. On hold. Nothing is sent and the column stays Pending. Held pending the decision on independence from OTL (§1). The Project Costing post in §4 does not go through OTL, so time still reaches costing while this is on hold.
This replaces a push with a pull, and most of it already exists. PARTNER_STATUS used to track a direct hand-off that wrote into the main O2C application’s accrual tables. That is superseded: accrual will pull from a table in our schema instead.

Worth knowing before the structure is agreed — the interface behind ACCRUAL_STATUS is already a pull, already day-wise and never rolled up, already carries the Reversal and Adjustment rows with a link back to the adjustment they came from, and already has the claim-a-batch-once bookkeeping a puller needs. So of the three things required, the complete timesheet and the adjustments are in place in some form. The genuine gap is the summary grain — that table holds day rows only.

Which raises the question to settle before the accrual side finalises anything: is this one interface or two? If accrual pulls everything from one place, then ACCRUAL_STATUS and PARTNER_STATUS are tracking the same hand-off and should collapse into one column. If they stay separate, the split needs to be deliberate — for example summary against one and detail against the other — rather than an accident of the push having been replaced. Two pull interfaces for one consumer, filled by the same confirm step, is the shape most likely to drift apart.

4What is sent to Oracle Project Costing

Approved hours are posted directly by REST to the Unprocessed Project Costs resource. This supersedes the earlier assumption that costing could only be reached by a scheduled transfer process: the resource accepts a third-party cost by POST, and Fusion’s Import Costs program then turns unprocessed costs into project costs.

4.2 What is not sent

  • Leave. Rows marked IS_LEAVE = 'Y' are excluded. Absences originate in Absence Management, which already reaches costing — posting them here would double-count.
  • Unapproved hours. Only entries whose day status is Approved, in a month that has been confirmed.
  • Cost and bill rates. We send quantity; Oracle applies rates and burdening.
  • Anything to payroll, per §1.

4.3 Reversals and adjustments

A retro adjustment is a matched pair — a negative reversal of the original day and a positive re-entry. Both post as ordinary rows, the negative carrying ReversedOriginalTransactionReference pointing at the entry it offsets. Hours are signed throughout, so the recipient can sum and get the net position with no sign logic.

4.4 Confirming it landed

  1. POST returns UnprocessedTransactionReferenceId and StatusCode = 'P' (pending).
  2. Fusion’s Import Costs program converts them to project costs.
  3. GET …?q=StatusCode='R'&expand=Errors lists rejections with the reason.
  4. PATCH to correct a rejected row, or DELETE to discard it, then re-process.

Step 3 needs a home: rejections surface in Fusion and somebody has to see them. Recommended — a scheduled read of rejected rows written back to the module, so the Accrual Integration screen shows a failed post instead of it being silently lost.

6Test data preparation, by revenue model

Agreed: the functional team will prepare the data. Every scenario has to be exercised against each revenue model, because the rules that fire are different for each — and today only one model has data behind it at all.

6.1 The three revenue models, and what each has to exercise

Revenue modelWhat is different about itData needed to exercise it
T&M
Time & Material		 Hours are the billable unit. The straightforward path: capture, approve, cost. Leave-loss does not apply. A project with a manager, at least two chargeable WBS tasks, and resources allocated at 100% and at a part percentage. Absence inside the month, to prove leave shows without triggering leave-loss.
FCP
Fixed Capacity		 The only model where leave-loss applies. Absence on a billable allocation is a loss of committed capacity, so PROC-006 / RULE-014 fire — and both gate on revenue model and the leave-loss flag together. This is the richest case and the one most likely to be missed. A project with revenue model = FCP and leave loss = Yes; an allocated resource with an approved absence on a working day; and a second eligible resource available on the same dates, so cover assignment can be exercised. Also a project with FCP but leave loss = No, to prove the rule declines it.
Milestone Revenue is not driven by hours. Time is still captured, approved and costed, but nothing about the revenue position follows from the hours. A project with a manager and chargeable tasks, and an allocated resource. Confirms that capture and the cost post behave identically while no revenue rule engages.

The distinction matters because the leave-loss refusal is explicit: coverage applies only to FCP projects with leave loss set to Yes. Test data that is all T&M will never reach that rule, and test data that is all FCP will never prove the rule declines the others.

Blocker to resolve first — the revenue model has no source. REVENUE_MODEL and LEAVE_LOSS_FLAG are commercial attributes this module owns. They are not read from Fusion and never have been — they were deliberately excluded from the old extract as values the module sets itself, and they are null for every project that arrived that way. With the extract removed and all project data now read live from Fusion (§2), these two have no source at all.

So data cannot be “prepared for each revenue model” until we decide where the value lives. Two options:

(a) Map it from a Fusion attribute. The project resource carries user-definable code and text slots (ProjectCode01 onward) which is exactly where a value like this is normally held. One of them is nominated, the functional team populates it per project, and the module reads it with everything else. Preferred: the data then lives with the project, one place, maintained by the people who own the commercial terms.

(b) Keep it local to this module. A small maintained mapping of project number to revenue model and leave-loss flag. Works, but it is a second place to keep current, and a project whose commercial basis changes in Fusion will not change here.

Until one is chosen, leave-loss cannot fire for any project, because the rule requires a value that nothing sets.

Two transitions are easy to miss and both matter. Rejected → Submitted is the correct-and-resubmit loop, and it resets every day to Pending — without that reset the manager could not act on the week again. Approved → Submitted is a manager undoing their own decision; it deliberately returns to Submitted and never to Not yet submitted, because the employee did submit and must not be made to send it again.
