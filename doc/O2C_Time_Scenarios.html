Scenarios, statuses and flags

Every situation the module has to cope with, with the employee status, the manager status and the flags each one produces. Written against the built code, not the intention — where the code does something other than expected, that is recorded rather than tidied away.

1How to read this

Two status axes, not one. The employee’s act and the manager’s decision are independent facts, and describing them separately says more than a single combined status can.

AxisValues
Employee statusNot yet submitted · Submitted
Manager statusPending · Approved · Rejected
SystemDefaulted — produced by a cut-off job, with no actor at all
FlagsLate submission · Defaulted · Overridden · Revoked · Advance closure · Reversal · Adjustment

A flag is an exception marker. The clean path — submitted on time, approved on time — carries no flag at all. Four actions always raise one (both withdraws, correct, and the cut-off jobs), one raises one conditionally (submit, only when late), and three never do (approve, reject, save).

9Absence correction

Absence is read live per person per date, so a new absence appears the moment the screen reopens. Everything else about a changed absence is the problem.

#ScenarioEmployeeManagerEffect
26Absence added before submitNot yet submitted—Leave row appears on the next page load. Clean
27Absence added after submitSubmitted — frozenPendingThe leave row is not added. The manager approves hours that ignore the leave. Needs a reject and resubmit, or a manager override
28Absence added after approvalSubmittedApprovedRetro adjustment territory
29Absence cancelled or shortenedanyanyThe leave row survives. The absence merge inserts and updates but never deletes, so leave is overstated and worked hours understated
30… and the employee tries to remove it——They cannot. Leave is system-owned (RULE-008): the button is suppressed and the server refuses
31Absence extendedanyanyThe extra days appear only if population runs again
32Absence corrected after the month is confirmed——Leave is excluded from costing but included in accrual, so the accrual figure moves. Needs a retro adjustment and an accrual top-up
Nothing reconciles a leave row against an absence that later changed. Scenario 29 is the dangerous one: it is silent, the numbers are wrong in a direction nobody notices, and the person it affects has no way to correct it.

11The client does not accept the hours

Half of this is already modelled: Client is a valid rejection reason (RULE-013), and UNBILLED_REASON exists with a constraint that forces it whenever a row carries hours and is non-billable.

#When the client disputesEmployeeManagerMechanism
42Before approvalSubmittedRejectedReject with reason Client — supported today
43After approval, before the month is confirmedSubmittedPendingManager undoes the decision (Revoked), then rejects or overrides
44After confirmation, accrual and the costing post——Rejection is no longer available. Retro adjustment: Reversal(−) of the billable hours and Adjustment(+) of the same hours as Non-billable with an unbilled reason. Net hours unchanged, billability changed — the person did the work
45Client accepts fewer hours than logged——Only the difference becomes non-billable. Hours that were worked are never deleted
46Client rejects the hours entirely——Reversal(−) with no re-entry
A scope question to settle before 44 is built. We send quantity and POET to Project Costing, and Oracle decides billability from the task’s own flag. So flipping our billable type changes our accrual and reporting — it does not change what Oracle bills. If a client rejection is also expected to reverse the Oracle-side cost, that is a different integration and it is not in scope today.

12Adjustment driver — who caused it

Proposed, not built. Today an adjustment records its shape and its reason text, but not who drove it — and that is the thing everybody downstream wants to know.

What exists todayValuesWhat it tells you
ADJ_KINDRetroWBS · DefaultCorrectionthe shape of the adjustment
REASONfree textwhatever somebody typed
nothing—who caused it

Proposed: a driver on the adjustment, using the same three-value shape the rejection reason already uses, so the two read consistently.

DriverMeansTypical trigger
Employee driven The person booked it wrongly and is correcting their own entry Wrong task, wrong project, wrong day, hours mistyped
Manager driven The approver changed what was booked, or corrected it after the fact Override after the month closed; reallocating effort between tasks; correcting a defaulted week
Client driven The client would not accept the hours as billed Scenarios 44 to 46 — hours moved to non-billable, or reversed outright

Three reasons this earns its place rather than being another column. It travels to accrual — a client-driven reversal is a commercial event and an employee-driven one is a bookkeeping correction, and the consumer currently cannot tell them apart. It is reportable — “how much did we write off because clients rejected it” is a question free text cannot answer. And it matches the existing rejection reason, which already distinguishes Manager, Client and Absence, so the module would say the same thing the same way in both places.

What it would take. One column on the adjustment with a three-value check constraint; the value carried onto the interface row beside the existing flag, so accrual receives it; and one field on the adjustment dialog. The Absence value the rejection reason carries has no equivalent here — an absence correction is a system event with no human driver, which is itself worth deciding: either a fourth value, or left null.

13Three findings worth acting on

#FindingWhy it matters
29 A cancelled absence leaves its leave row behind Silent. Leave is overstated, worked hours understated, and the employee cannot correct it because leave is system-owned
7 A never-submitted, never-approved week has no second safety net Weekly defaulting picks up only Not yet submitted; delivery defaulting picks up only Submitted. Once the weekly job sets Defaulted, the delivery job can never see it, so the week sits locked with nobody prompted
44 No route from approved to non-billable The plumbing exists — UNBILLED_REASON and the constraint behind it — but there is no screen action, so a client rejection after confirmation has nowhere to go
