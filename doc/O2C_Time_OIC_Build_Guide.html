O2C Timesheet Module

Building the OIC sync — step by step

Adapting the PWP AR Invoice Headers pattern to the timesheet master-data load: one monthly run and two daily runs, feeding the ORDS endpoints that already exist.

09 August 2026 3 integrations 11 data models verified against dev20

Read section 1 before cloning anything. Three parts of the PWP template do not transfer, and one of them — the watermark — cannot work at all with these data models. Cloning first and discovering that later means unpicking the orchestration.

1 What does not transfer from the PWP template

1.1 The watermark cannot filter anything

PWP is a changed-since sync: it reads a last-sync date, passes it to the report, and gets back only what moved. None of the eleven timesheet extracts supports that. Their only bind is :P_EFFECTIVE_DATE, and it is an as-of date for HCM's effective-dated tables (_F/_M), not a change filter. Checked across all eleven: no LAST_UPDATE_DATE predicate anywhere.

So every run returns a full snapshot as of a date. A watermark passed into the report would change nothing about what comes back.

Do this instead: full refresh, every run. It is not a compromise here —

  • every ORDS sync endpoint is a MERGE on the natural key, so a repeated row is an update and a re-run is free;
  • a full refresh is self-healing: it repairs anything a missed delta would have left stale, which an incremental sync silently cannot;
  • the volume does not justify the complexity — all eleven extracts together are about 11,800 rows, measured on the pod on 09-Aug-2026.

If true deltas are wanted later, the change is in integration/bip/extracts.py — add a LAST_UPDATE_DATE predicate and a :P_LAST_SYNC bind, then redeploy the models. Do not try to solve it in OIC.

1.2 The watermark store already exists — do not build a second one

PWP keeps its own getLastSyncDate / putLastSyncDate. This module already records every run in OC_TIME_SYNC_JOB: job name, scope, status, rows read, rows upserted, rows failed, start and finish. It is written by the sync endpoints themselves and exposed read-only at GET /oc/time/admin/sync/status.

A second store in OIC would be a second version of the truth, and the two would disagree the first time a run half-failed. Drop the getWatermark and updateWatermark scopes; read sync/status if a run needs to know what happened last time.

1.3 The chunk loop is a download loop, not a paging loop

PWP's chunkLoop pages the report by row offset — reportOffsetAssignment, segmentCount >= RowCount. That needs the report to take an offset parameter. Ours do not.

What BIP offers here is byte-level chunked download of one result: downloadReportDataChunk(fileID, beginIdx, size) where beginIdx and size are bytes, not rows. The report runs once; you collect its output in pieces.

Practically: only WORKERS (5,988 rows) is big enough to need it. The other ten come back in a single response.

3 The child integration — build this once

One app-driven integration, parameterised by entity. Three orchestrators call it; you do not build eleven of these.

Name: O2C_TIME_LOAD_ENTITY  ·  Trigger: app-driven (REST)  ·  Inputs: entity, effectiveDate, actor, traceId

3.1 Scope: resolveEntity

Map the entity name to its data model path and its loader endpoint. Keep this in one lookup, not scattered across the flow — it is the only place the two are tied together.

entitydata modelloader endpoint
WORKER/Custom/O2C_TIME/O2C_WORKERS.xdmPOST sync/worker
PROJECT/Custom/O2C_TIME/O2C_PROJECTS.xdmPOST sync/project
TASK/Custom/O2C_TIME/O2C_TASKS.xdmPOST sync/task
ALLOCATION/Custom/O2C_TIME/O2C_ALLOCATIONS.xdmPOST sync/allocation
CALENDAR/Custom/O2C_TIME/O2C_CALENDAR.xdmPOST calendar/sync/CORPORATE
WORKER_SHIFT/Custom/O2C_TIME/O2C_WORKER_SHIFTS.xdmPOST calendar/sync/SHIFT

SHIFTS, WORK_PATTERNS, WORK_SCHEDULES and EXP_TYPES are deliberately absent: they have no target table today, so there is nowhere to load them. Leave them as on-demand models for investigating a wrong shift.

3.2 Scope: runBipReport

  1. Invoke runDataModel on ExternalReportWSSService, with reportAbsolutePath = the model path, attributeFormat = xml, and one parameter P_EFFECTIVE_DATE = the input date as YYYY-MM-DD.
  2. Assign extractReportBytes — the response carries reportBytes (base64) and, when the result is large, reportFileID.
  3. Switch: if reportFileID is present, enter the download loop; otherwise go straight to staging.
  4. While downloadLoop — invoke downloadReportDataChunk(fileID, beginIdx, size), append, advance beginIdx by the bytes received, exit when a chunk comes back empty. beginIdx is a byte offset.

The bind must be declared in the data model or the report returns nothing. An undeclared :BIND in a BIP data model resolves to NULL with no error at all — the report simply returns zero rows, which reads exactly like "there is no data". Every model was generated with the parameter declared; if one is ever hand-edited in the BIP UI, check the parameter list still matches.

3.3 Scope: stageAndTransform

Read the XML into a stage file. The envelope is <DATA_DS><ROWSET><ROW>, one <ROW> per record, element names exactly as the canonical column names.

Map each ROW to the loader's row shape. Two conversions are mandatory and both fail silently if missed:

  • Dates must be YYYY-MM-DD strings, no time part.
  • APPROVAL_STATUS must be exactly Approved. Fusion returns APPROVED in capitals; populate_month filters on 'Approved'. Wrong case caches perfectly well and then never becomes a timesheet row — it fails at the last step, which is the worst place for it to fail.

3.4 Scope: postToOrds — chunked

While loop over the staged rows in batches of 500:

POST /oc/time/admin/sync/{entity}
{
  "jobRunId": null,          // OMIT on the first chunk — the loader creates the
                             // job and returns its id
  "final":    "N",           // "Y" on the last chunk only
  "actor":    "OIC_MASTER_SYNC",
  "traceId":  "<the OIC instance id>",
  "rows":     [ { ...500 rows... } ]
}

response: {"jobRunId": 47, "upserted": 500, "failed": 0}
  • Capture jobRunId from the first response and pass it back on every later chunk. Omit it and each chunk opens its own job row, so a 5,988-row load reports as twelve unrelated runs.
  • Set final: "Y" on the last chunk. That is what closes the job as Success or Partial. Miss it and the job sits at Running for ever and the Sync Status screen shows a run that never ended.
  • A bad row never aborts a chunk. It lands in OC_TIME_SYNC_FAILED with its reason and the job closes Partial. Treat Partial as a warning with a report, not as a failure.

4 The monthly orchestrator

Name: O2C_TIME_MASTER_MONTHLY  ·  Trigger: schedule, 28th at 20:00 local, per payroll country

  1. Assign effectiveDate = the 1st of next month. Not today. The monthly run builds next month, so the HCM as-of date must be inside next month or you populate from this month's allocations.
  2. Call the child, in this order — WORKER, PROJECT, TASK, ALLOCATION, CALENDAR, WORKER_SHIFT.
  3. Invoke POST /oc/time/admin/jobs/populate/{periodId} with an empty body — no employeeId, which is what makes it populate every allocation.
  4. Logger — job ids and row counts from each child.

The order is not stylistic — sequence it, do not fan out. OC_TIME_ALLOCATION has foreign keys to both worker and project, so an allocation row whose worker has not loaded yet lands in OC_TIME_SYNC_FAILED instead of the table. Parallel branches will half-work and look fine.

Passing employeeId in the populate call is the difference between one person and everybody. The operation's own schema says so: "Omit to populate every allocation." The monthly run wants everybody, so the body is empty — but be deliberate about it, because the same endpoint scoped to one person is what the timesheet page calls on every load.

5 The daily orchestrator

Name: O2C_TIME_MASTER_DAILY  ·  Trigger: schedule, twice a day per country — 09:00 and 15:00 local is a reasonable start

  1. Assign effectiveDate = today.
  2. Call the child in the same order. Same full refresh — §1.1.
  3. Invoke POST /oc/time/admin/jobs/daily.

Why twice, and why per country. Straight from the BRD: "if you ran this program at 8 in the night in India, US data may not even be inside — you might have to run it 2 or 3 times." OC_TIME_PERIOD is already keyed by PAYROLL_COUNTRY, so the data model supports it; nothing in the module reads a time zone, so the split has to live in the OIC schedule.

Three change types the BRD names have no code path at all. populate_daily handles allocation change, project and WBS moves and new hires. Termination reversals, deputations and transfers are not implemented. Switch the daily schedule on today and those will silently never apply — the job will report success. Build them before go-live or record the gap explicitly.

  • Country list and run times agreed
  • The three missing daily triggers built, or the gap accepted in writing
  • Someone owns the Partial report — a failed-row queue nobody reads is the same as no validation
