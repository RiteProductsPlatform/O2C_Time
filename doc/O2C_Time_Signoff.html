O2C · Time Module · for approval

Scope and integration sign-off

What the module does, what it deliberately does not do, which data is fetched live from Oracle Fusion versus synced on a schedule, how time is prepopulated, the complete status and flag model, and exactly what is posted back to Oracle Project Costing.

Version 1.0 Prepared 05-Aug-2026 Source: REQ-PACK-TIME-001 v0.3 Branch O2C_Time_Integration

1Scope

Oracle Time & Labor is being replaced for project time capture and approval. Oracle remains the system of record for costing: we capture and approve time, then post approved hours to Project Costing.

In scope

  • Time capture — day-wise entry per project and WBS task, multiple lines per day, quarter-hour granularity.
  • Prepopulation from allocation percentage and from approved absences (§3).
  • Approval — day, week and project-month, with reason and remarks on rejection, and an undo for a decision taken by mistake.
  • Manager override of hours with the employee's original value retained.
  • Retro adjustments on a closed month, as a matched reversal and re-entry.
  • Cut-off enforcement — weekly (employee) and delivery (manager), with automatic defaulting at each.
  • Salary-stop signal for employees who missed the weekly cut-off.
  • Leave-loss / cover identification for absence on billable allocation.
  • Month confirmation to the O2C accrual interface.
  • Post to Oracle Project Costing via unprocessedProjectCosts (§4).
  • Own sign-in and roles — employee, contractor, manager, finance administrator.

Out of scope

  • Payroll — entirely out of scope. No hours are transferred to Global Payroll, nothing is written to elementEntries, no Payroll Time Type is resolved and no payroll reference data is read. The salary-stop signal in scope above is a flag for the payroll team to act on, not a payroll transaction.
  • Invoice generation and revenue calculation.
  • Writing to Project Costing beyond the unprocessed-cost post — costing, burdening and accounting stay Oracle's.
  • Absence creation. Absences are read from Absence Management and shown read-only; they are never created or amended here.
  • Calendar and shift authoring. Sourced from Fusion; no maintenance screen.
  • Period control screen. Periods and cut-offs are reference data, exposed read-only.
  • Mobile — phase 2.
  • Direct Fusion calls from the browser with credentials in the client (NFR-005). All Fusion traffic is server-side or proxied.
  • Timesheet upload (CSV in). Download exists; upload is on hold by decision.
Note on payroll. Oracle delivers three OTL time consumers — Payroll, Project Costing and Absence Management. This module feeds Project Costing only. That is a deliberate narrowing of the OTL model, and it is why the routing logic Oracle calls a “time consumer set” does not appear in this build: there is one destination for cost, so there is nothing to route between.

2Inbound integrations

Two mechanisms, chosen per data domain by how the data is used rather than by preference. Per the functional decision of 05-Aug-2026, project, POET, allocation and absence are fetched live from Fusion as the screen loads. Bulk reference data that batch jobs must walk for every employee at once stays on a scheduled BIP sync.

2.1 Fetched live from Fusion, on page load

Read per user, at the moment the screen needs it. Nothing is staged first, so a project assigned this morning is selectable this morning.

#DataFusion REST resourceWhat it is, and why we need it
INT-002 Projects the person may charge to GET /fscmRestApi/…/projectLaborResources
GET …/projects		 The projects a person is a labour resource on, with project number, name, customer and manager. Why: it is the Project picker on the timesheet, and the project manager on it is who the week routes to for approval. Read live because a new assignment must not wait for an overnight sync before the person can book time to it.
INT-002 WBS tasks and chargeability GET …/projects/{ProjectId}/child/Tasks
GET …/projectFinancialTasks		 The task breakdown under a project and whether each task is chargeable and billable. Why: hours are booked against a task, not a project — the task is the “T” of POET and decides whether the time is billable. Read live so a task added to the WBS mid-month is immediately selectable.
INT-002 POET completion
(expenditure type, expenditure organization)		 GET …/expenditureTypes
expenditure org from the person's assignment		 Expenditure type classifies the work for costing; expenditure organization is the unit that incurs the cost. Why: Project Costing rejects a cost whose POET is incomplete. These two are the pieces the module did not previously hold, and without them nothing can be posted at all.
INT-003 Allocation / assignment GET …/projectResourceAssignments
GET …/personAssignmentLaborSchedules		 Which person is assigned to which project, at what percentage, over which dates. Why: the allocation percentage is what the timesheet is prepopulated from (§3), it drives the “My allocation” panel, and it determines whose time a given manager sees. personAssignmentLaborSchedules is additionally the only source of a per-POET percentage split.
INT-006 Absences GET /hcmRestApi/…/absences Approved absence per person per date, with type and duration. Why: leave appears on the timesheet as read-only hours so the week reconciles to standard hours, and absence on a billable allocation is what triggers leave-loss. Read live because leave is booked continuously and a stale answer shows the wrong reason for a short week.

2.2 Synced on a schedule by OIC (BIP runReport)

Bulk, set-based reference data. The batch jobs that build a month walk these for every employee at once, which per-user live calls cannot do at acceptable cost. Invoked directly over SOAP; no file hand-off.

#DataCadenceWhat it is, and why we need it
INT-001 Workers Daily Employee id, name, email, worker type, legal employer, expenditure organization, standard hours per day, line manager, hire and termination dates. Why: identity and the approval hierarchy. Standard hours per day is the multiplicand for prepopulation; the line manager is who a manager's own timesheet is approved by. Synced because sign-in cannot depend on a live Fusion call, and because every batch job needs the whole population.
INT-005 Calendar and holidays Monthly Public holidays and non-working days by country and location. Why: a non-working day is not prepopulated and is tinted on the grid. Needed for every employee for a whole month before the month is built, so a per-day live lookup would be thousands of calls for data that changes once a year.
INT-004 Shifts, work patterns, work schedules Monthly The shift a person works on a given day and the hours it implies. Why: the read-only Shift row on the timesheet and the standard hours per day. Must stay BIP: Oracle's own REST documentation states a person's assigned work schedule is not a first-class REST resource.
INT-002 Expenditure-type reference On change The legal list of expenditure types with unit of measure. Why: validates the configured default before it is used on a cost. Only 30 of 262 types on the reference pod are measured in hours — several named “… Labor” are in dollars and would be wrong.
Two dependencies to confirm. (a) Fusion PersonId and AssignmentNumber are not currently extracted. The columns exist and nothing populates them. Project Costing accepts PersonNumber, so the post in §4 can proceed, but any absence call keyed on the person and any future OTL interaction needs these. Both are on an assignment table already joined by the worker extract. (b) “Time Card Required” eligibility is not sourced — the flag that says a person should report time at all. Until it is, the module will accept time from anyone with an allocation.

3The time module — prepopulation, status and flags

3.1 What is prepopulated, how, and when

The month exists before anyone opens it. Two passes, in this order.

Pass 1 — allocated project time

For every active allocation overlapping the period, for every day in the period:

StepRule
Skip the dayif it is a non-working day — weekend or holiday. Nothing is seeded, not even a zero. Saturday and Sunday still appear as blank, enterable cells.
Hoursstandard hours for that day × allocation % ÷ 100, rounded to the nearest quarter hour. A null allocation percentage is treated as 100. An 8-hour day at 50% seeds 4.00.
Taskthe project's first chargeable WBS task in sort order. If the project has none, nothing is seeded for that allocation and the reason is recorded as a failed record — visible on Sync Status, not silent.
Markingthe row is stamped SOURCE = 'Prepopulated' and ENTRY_TYPE = 'Actual'.
Idempotentan existing row for the same week × project × task × day is never overwritten, so re-running never destroys typed hours.
One allocation, one line. Prepopulation loops allocations, not people. Two active allocations produce two lines, each apportioned separately, and the sum is not capped at this point — a person holding two 100% allocations is seeded 16 hours a day. The 24-hour rule catches it later, on the day total. Worth confirming that concurrent 100% allocations are a data condition to be corrected in Fusion rather than something the module should silently cap.

Pass 2 — approved absences

Approved absences in the period are written as read-only leave rows at their own duration, against a common LEAVE task, marked IS_LEAVE = 'Y'. Allocation percentage is not applied — leave is whole. The row is attached to one of the person's active allocations because an entry requires a project. An employee with no active allocation gets no leave row, and nothing reports it — an open item.

When it runs

JobTriggerWhat it covers
Monthly populationOnce per period, before the month opensEvery active allocation for every active worker.
Daily processDailyOnly employees whose allocation or worker record changed that day — new hire, exit, transfer, allocation change, shift change. Re-runs the monthly logic for that person.
Weekly defaultingAt the weekly cut-offAn unsubmitted week is auto-submitted with default hours, marked Defaulted and locked.
Delivery defaultingAt the delivery cut-offA week the manager never decided is marked Defaulted, and is not locked.

All four are endpoints with no timer of their own — OIC owns the schedule. Order matters: the master sync must finish before monthly population, or the month is built from last month's allocations; and the salary-stop job must run after weekly defaulting, because it acts only on weeks that job marked.

3.2 Status

A record is in exactly one status at a time, at each of three grains.

GrainTable · columnValues
Week (the main one) OC_TS_WEEK.WEEK_STATUS Not yet submitted · Submitted · Approved · Rejected · Defaulted · Overridden and approved · Closed (7)
Day OC_TS_ENTRY.DAY_STATUS Pending · Approved · Rejected (3)
Project-month OC_TS_MONTH_CONFIRM.CONFIRM_TYPE Normal · Advance closure · Reopened (3)
Retro adjustment OC_TS_ADJUSTMENT.STATUS Awaiting Approval · Approved · Rejected · Cancelled (4)
Outbound destination OC_TS_MONTH_CONFIRM.OTL_STATUS, ACCRUAL_STATUS, PARTNER_STATUS Pending · Success · Failed · Skipped, each independently

The three outbound columns are separate deliberately: the destinations fail independently, and one combined column loses which of them needs attention.

3.3 Flags

A flag is not a status. Status is where the record has got to; a flag records something that happened on the way and stays true afterwards. A week carries any number of flags at once, all on OC_TS_WEEK.

FlagColumnSet byMeaning — and what it does not mean
Defaulted DEFAULTED_FLAG + DEFAULTED_BY the two defaulting jobs Hours were filled in by a cut-off job rather than by a person. DEFAULTED_BY distinguishes EMPLOYEE (missed the weekly cut-off — holds salary) from MANAGER (missed the delivery cut-off — never holds salary).
Late submission LATE_SUBMISSION_FLAG submit, when past the cut-off The week arrived after the cut-off. It is a flag, not a status — the week is still Submitted. Deliberately never cleared: revoking or resubmitting does not un-happen it.
Advance closure ADVANCE_CLOSURE_FLAG advance approval of a future month The month was closed ahead of its cut-off; defaulted hours in it are treated as approved.
Overridden & approved OVERRIDDEN_FLAG manager override A manager changed the hours and approved them. The employee's original value is retained in the audit trail. Also becomes a status when the week closes — see 3.4.
Reversal HAS_REVERSAL_FLAG derived automatically The week contains at least one negative reversal row. Recomputed from the entries, never set by hand.
Adjustment HAS_ADJUSTMENT_FLAG derived automatically The week contains at least one retro adjustment row. Same derivation.
Locked LOCKED_FLAG weekly defaulting Mechanical, not a business flag: the week can no longer be edited by the employee. Only weekly defaulting locks; delivery defaulting does not.

3.4 How status and flag relate

Three distinct relationships, and they are easy to conflate:

  1. Orthogonal. One status, many flags. A week can be Submitted + Late submission + Adjustment simultaneously.
  2. Two values are both. Defaulted and Overridden and approved appear as a week status and as a flag. The status says what the week is now; the flag says it happened at all and survives a later transition — a defaulted week that a manager then approves becomes Approved while DEFAULTED_FLAG stays 'Y'. Whether to keep this duplication is an open item.
  3. Precedence, when only one label can be shown. The accrual interface and the chips on screen must pick one. The order, most specific first: row is a Reversal → row is an Adjustment → Advance closure → Overridden & approved → Defaulted → Late submission → none.

Where each is maintained

TableHolds
OC_TS_WEEKthe week status, all six business flags, LOCKED_FLAG, DEFAULTED_BY, submit/approve stamps, reject reason and remarks
OC_TS_ENTRYDAY_STATUS; ENTRY_TYPE (Actual · Default · Reversal · Adjustment), which is what the reversal and adjustment flags are derived from; IS_LEAVE; SOURCE
OC_TS_APPROVALthe decision trail — one row per event: Submit · Resubmit · Approve · Reject · Override · AdvanceApprove · Confirm · Default · Release · Revoke, with actor, granularity and timestamp
OC_TS_AUDITvalue changes with the before-image — Override · Adjustment · Reversal · ManagerEdit · Import · DefaultCorrection
OC_TS_MONTH_CONFIRMthe project-month confirmation and the three independent outbound statuses
OC_TS_ADJUSTMENTretro adjustment lifecycle

Rejection carries a reason — Manager, Client or Absence — and it is mandatory, enforced by a constraint rather than by the screen. Remarks are free text.

4What is sent to Oracle Project Costing

Approved hours are posted directly by REST to the Unprocessed Project Costs resource. This supersedes the earlier assumption that costing could only be reached by a scheduled transfer process: the resource accepts a third-party cost by POST, and Fusion's Import Costs program then turns unprocessed costs into project costs.

POST /fscmRestApi/resources/11.13.18.05/unprocessedProjectCosts

4.1 What we send, and where it comes from

One row per approved entry. POET travels in the ProjectStandardCostCollectionFlexfields child block.

…ProjectStandardCostCollectionFlexfields — the POET block

_ORGANIZATION_ID_Display—O — expenditure organization
_EXPENDITURE_ITEM_DATE—the entry date — the day the work happened, not the day it was posted

4.2 What is not sent

  • Leave. Rows with IS_LEAVE = 'Y' are excluded. Absences originate in Absence Management, which already reaches costing — posting them here would double-count.
  • Unapproved hours. Only entries whose day status is Approved, in a month that has been confirmed.
  • Cost and bill rates. We send quantity; Oracle applies rates and burdening.
  • Anything to payroll. Per §1.

4.3 Reversals and adjustments

A retro adjustment is a matched pair — a negative reversal of the original day and a positive re-entry. Both post as ordinary rows, the negative carrying ReversedOriginalTransactionReference pointing at the entry it offsets. Hours are signed throughout, so the recipient can sum and get the net position with no sign logic.

4.4 Confirming it landed

  1. POST returns UnprocessedTransactionReferenceId and StatusCode = 'P' (pending).
  2. Fusion's Import Costs program converts them to project costs.
  3. GET …?q=StatusCode='R'&expand=Errors lists rejections with the reason.
  4. PATCH to correct a rejected row, or DELETE to discard it, then re-process.

Step 3 is the part that needs a home: rejections surface in Fusion, and somebody has to see them. Recommended — a scheduled read of rejected rows written back to OTL_STATUS / OTL_MESSAGE so the Accrual Integration screen shows a failed post instead of it being silently lost.
